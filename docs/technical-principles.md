# 技术原则

## 1. 先理解底层机制，再使用高级封装

先理解 HTTP/SDK 模型调用、消息格式、工具调用请求与返回，再使用 LangChain 等框架简化实现。学习框架不是背 API，而是理解抽象解决的问题。

## 2. 先单 Agent，再 Multi-Agent

先让一个 Agent 稳定完成任务，再判断是否需要拆分角色。多 Agent 会增加通信、状态、延迟、成本和调试复杂度，不应为了使用新技术而强行采用。

## 3. 区分 Workflow 与 Agent

- Workflow（工作流）：步骤和控制流主要由开发者预先定义。
- Agent（智能体）：模型可以在给定边界内动态选择下一步行动或工具。
- 混合架构通常更适合生产系统：确定性流程负责安全与关键步骤，Agent 负责需要模型判断的部分。

## 4. 技术栈建议

- Python：Agent 后端与工具实现。
- FastAPI：对外提供服务 API。
- LangChain：模型接入、提示词、输出解析和工具/Agent 应用开发。
- LangGraph：有状态流程、条件路由、循环、持久化和人工审核。
- React + React Flow：对话界面、任务计划和执行状态可视化。
- MySQL：真实业务数据和只读查询实践。
- MCP：标准化工具、资源和提示模板的接入。
- RAG 与向量数据库：在知识检索场景出现时再引入，避免过早选型。
- Docker：在生产部署阶段逐步引入。

框架/API 可能变化，编写课程和代码时应核对对应版本的官方文档。

## 5. 模型与供应商解耦

通过环境变量管理模型供应商、模型名称、API 地址和密钥。尽量把业务逻辑与具体供应商的 SDK 解耦，避免将密钥写入源码或提交到 Git。

## 6. 工具执行由应用程序负责安全控制

模型提出工具调用不等于工具必然执行。应用程序必须验证：

- 当前用户身份与团队归属。
- 用户是否拥有目标资源的权限。
- 工具参数是否符合 Schema。
- 操作是否在允许范围内。
- 是否需要人工审批。
- 执行结果是否需要脱敏或审计。

数据库实战默认从只读账号和只读查询开始。不要把安全寄托在 Prompt 上；数据库权限、SQL 限制、超时、行数上限和审计必须由程序强制执行。

## 7. 从早期开始重视可靠性

逐步加入：

- 输入与输出校验。
- 超时、有限重试与错误分类。
- 终止条件，防止 Agent 无限循环。
- 幂等性与重复执行保护。
- 结构化日志、执行追踪和指标。
- Token、延迟和调用成本统计。
- 回归测试与评测集。

重试策略要区分可重试错误和不可重试错误；有副作用的操作不能盲目重试。

## 8. Memory 与 RAG 不等同

- Memory（记忆）：保留与后续交互或任务执行相关的状态、偏好或历史信息。
- RAG（检索增强生成）：从外部知识源检索相关内容，再提供给模型生成答案。
- 对话历史、持久化任务状态、长期记忆和知识库是不同概念，不应混为一谈。

## 9. MCP 不等同于 Agent

MCP（Model Context Protocol，模型上下文协议）用于标准化模型应用与外部工具、资源等能力的连接。MCP Server 可以被不同客户端使用；Agent 则负责在具体任务中决定如何使用可用能力。两者相关但不等价。

## 10. 评测优先于主观感觉

至少考虑任务成功率、工具选择与参数正确率、结果正确性、引用质量、延迟、成本和安全边界。修改模型、Prompt 或工具后，应运行固定测试集比较结果。

## 11. 生产部署的安全原则

- 最小权限与团队/租户隔离。
- 对高风险操作设置人工审批。
- 保护密钥与敏感数据。
- 限制工具的能力范围、运行时长和资源消耗。
- 防范 Prompt Injection 与不可信工具输出。
- 保留必要审计日志，并控制日志中的敏感信息。
- 将 Agent 生成内容视为待验证输入，而非天然可信的指令。

## 12. 代码与项目组织

课程文档、示例代码和综合项目分开管理。每阶段提供依赖版本、运行方式、测试和 README。项目中逐步记录架构决策及其取舍。
