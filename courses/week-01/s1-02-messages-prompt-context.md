# S1-02：Message、Prompt、Token 与上下文窗口

建议用时：90–120 分钟。前一节讲模型如何接入，本节让同一个项目能连续对话，并解释模型本次到底能看到哪些信息。

## 1. 学习目标与前置知识

本节结束后，你应能够：

- 区分 Message、Prompt、Context 与 Context Window。
- 解释模型为什么能回答“刚才我说的是什么数据库”。
- 用 LangChain 与真实模型服务实现多轮文本对话。
- 保存完整 user / assistant 轮次，按轮次裁剪，并处理失败后的状态。
- 读取服务返回的 Token 用量，理解上下文预算与输出预算的区别。

前置知识：S1-01 的模型配置、HTTP / SDK 调用和 AIMessage。工程环境仍用 Python 3.12，依赖无需升级。代码可先阅读；真实联调仍需你自己的 API Key、模型权限和网络。

## 2. 核心术语（英文 + 中文）

| English | 中文 | 本节含义 |
|---|---|---|
| Message | 消息 | 一条带角色和内容的输入或输出 |
| Role | 角色 | system、user、assistant 等消息来源/用途标记 |
| Prompt | 提示 | 给模型用于完成任务的指令、问题、示例和上下文 |
| Context | 上下文 | 本次生成实际可使用的信息 |
| Conversation History | 对话历史 | 应用记录的先前消息；不一定全量发送 |
| Token | 文本处理单位 | 模型分词与用量统计使用的单位 |
| Context Window | 上下文窗口 | 单次处理时可容纳的 Token 容量上限 |
| Input / Output Tokens | 输入 / 输出 Token | 本次请求输入与生成结果的用量 |
| Reasoning Tokens | 推理 Token | 部分模型生成时使用、可能计入生成预算的 Token |
| Sliding Window | 滑动窗口 | 仅保留最近一部分对话作为工作上下文 |

## 3. 问题背景、原理与完整执行链路

### 从一个两轮对话开始

第一轮用户说“我使用的是 MySQL 8.0”，第二轮问“我刚才说的数据库版本是什么”。如果第二次请求只有第二句，模型就没有获得本次会话第一句中的版本信息。沿用同一个 API Key、同一个 HTTP Client 或同一个 ChatOpenAI 实例，都不等于把历史自动传入。

本课使用 Chat Completions、由应用手动管理历史。第二次请求应包含：

```python
messages = [
    {"role": "system", "content": "你是数据库学习助手。"},
    {"role": "user", "content": "我使用的是 MySQL 8.0。"},
    {"role": "assistant", "content": "好的，接下来结合 MySQL 8.0 讨论。"},
    {"role": "user", "content": "我刚才说的数据库版本是什么？"},
]
```

上面的 assistant 内容用于展示消息形状。实际代码保存真实服务返回的回答，不硬编码这段回答。模型是基于提供的信息继续生成，聊天并没有把“这个用户用 MySQL”永久训练进模型参数。

服务端会话管理接口也可以帮助管理状态，例如某些 API 的 conversation 或 previous_response_id；那是另一种集成方式。本课没有启用它们，不应把手动历史管理的行为外推为所有接口都必须手动重发。

### 为什么要保留 assistant 消息？

因为后一句可能引用的是上一条回答：例如“把你列出的第二种方案展开”。只保留用户输入，模型不知道自己上次列出的方案是什么。历史中的 assistant 消息是上下文，不是事实正确性的保证。

### 每轮代码的执行链路

1. 接收并验证新的用户问题。
2. 复制当前保留的 system 和历史消息，形成候选请求 pending。
3. 在 pending 末尾加入当前 user 消息。
4. 调用真实模型，接收 AIMessage。
5. 校验非空正文、未截断、没有本节不支持的工具调用。
6. 成功时一起保存本轮 user + assistant，裁剪最旧的完整轮次。
7. 失败时保留原历史，不追加半轮，不把错误提示当成模型回答。

这样下一次请求不会混入“没有对应答案的上次失败问题”。注意：本地未提交历史不代表供应商没有执行或计费，尤其是客户端超时。

## 4. 适用场景、方案比较与常见误区

| 策略 | 适合什么 | 局限 |
|---|---|---|
| 只发当前问题 | 独立翻译、分类、没有历史依赖的任务 | 无法可靠引用前文 |
| 带上全部历史 | 短会话、快速建立原型 | 历史增长会增加输入，可能超限 |
| 最近 N 个完整轮次 | 关注近期内容、简单成本与长度控制 | 早期约束和事实可能被丢弃 |
| 按 Token 预算裁剪 | 需要约束单次输入大小 | 需适配模型分词/消息开销，仍要设计信息保留策略 |
| 摘要、结构化状态与检索 | 长任务和大量资料 | 摘要可能丢失细节，持久化与检索需要另外实现 |

本课采用最近 N 轮策略。它限制轮数，**不是严格的 Token 限制**：一条很长的用户消息就可能超出模型窗口。本课不会因为轮次较少就保证接口永不溢出。

提示设计的三个基础动作：说清任务、提供必要上下文、说明期望输出。例如“你是专家”很宽泛；“面向熟悉 MySQL 的开发者，用一句定义和一个例子解释只读账号，不声称访问了数据库”更便于评估。Prompt 约束不能替代数据库授权和程序校验。

把业务约束写入受应用控制的指令，把用户内容保留为用户消息；不要让用户通过一个 role 字段自由提升成 system。多用户部署时，要按身份和会话隔离历史，不能共用一个全局消息列表。

## 5. Token 与上下文预算

### Token 不等于字符或单词

模型用特定 Tokenizer（分词器）将文本变为处理单位。英文单词可能拆成多个 Token；中文也不能假定一字固定等于一个 Token。代码、数字、标点和不同语言的切分也不同。因此 `len(text)` 和消息条数都不能当成准确 Token 数。

精确预算需使用与所选模型相匹配的计数方法，并考虑消息封装、工具定义等额外开销。本课不对任意兼容服务套用一个分词器；先读取实际响应的 usage_metadata，观察服务报告的用量。计数缺失应显示“未知”，不能当作 0。

### 上下文窗口与输出上限

上下文窗口是单次请求可使用的容量，不是数据库可以存多少聊天记录。粗略规划时可写为：

```text
输入预算 ≤ 模型上下文窗口 − 预留生成预算 − 安全余量
```

这里的预留生成预算需要按模型规则包含相应推理 Token，不能重复扣同一部分。还需单独遵守模型的最大输出限制。

只作算术演示：假设窗口为 8192 Token，预留生成预算 1000、安全余量 512，则计划输入不超过 6680 Token。这些是教学数字，不是你当前配置模型的规格。

第一课的 `max_completion_tokens=2048` 是生成预算参数，不是“整个上下文为 2048”。把输出上限调低也不会自动裁剪请求里的旧消息。

### 为什么会话越长，输入往往越多？

前一轮生成的回答，下一轮重新发送时就成为输入的一部分。假设一个简化案例中，固定提示 50、每轮问题 20、每轮答案 30 Token（忽略封装开销）：

| 请求 | 本次输入 | 本次输出 |
|---|---:|---:|
| 第 1 轮 | 50 + 20 = 70 | 30 |
| 第 2 轮 | 50 + 20 + 30 + 20 = 120 | 30 |
| 第 3 轮 | 50 + 20 + 30 + 20 + 30 + 20 = 170 | 30 |

实际用量、缓存计费和模型行为取决于供应商；本表只解释输入如何累积。长会话也不保证模型准确利用所有早期信息，因此需要用任务表现评估上下文策略。

## 6. 可运行代码、文件结构、依赖和配置

本节在原项目中新增两个模块和测试，并抽出模型创建函数；第一课命令继续可用。

| 文件 | 用途 |
|---|---|
| `app/langchain_api.py` | 新增 create_model，共用模型配置 |
| `app/conversation.py` | 消息状态、调用、成功提交和按完整轮次裁剪 |
| `app/chat_cli.py` | 交互入口与用量显示 |
| `tests/test_conversation.py` | 多轮请求、裁剪、失败回滚、清空与会话隔离 |

核心调用代码位于 `Conversation.turn`：

```python
pending = [*self.messages, {"role": "user", "content": question.strip()}]
reply = model.invoke(pending)
```

完整文件还做响应校验，然后提交历史：

```python
completed = [*pending[1:], {"role": "assistant", "content": answer}]
self._messages = [pending[0], *completed[-2 * self.keep_turns:]]
```

这里 `pending[0]` 是固定 system 消息，`pending[1:]` 是对话部分。文本聊天的一轮正好是 user + assistant 两条，因此保留最近 N 轮取最后 `2 * N` 条。这个简化只适用于本课的交替纯文本消息；后续工具调用可能一轮产生多条消息，不能照搬按两条裁剪。

不要直接拿 `history[-6:]` 处理包含 system 的任意消息列表，也不要按字符随意截断整段 JSON。本课的系统提示单独保留，完整轮次一起移动。

如果之前已经创建并安装过相同环境，可直接使用。手动将 `.env.example` 复制一份，重命名为 `.env`（不是 `.env.txt`），填写 `LLM_API_KEY`、`LLM_MODEL`、`LLM_BASE_URL`。已有 `.env` 时保留自己的配置，不要覆盖。这样无需依赖 PowerShell 的 Copy-Item 命令。

```powershell

```

macOS / Linux 使用 `.venv/bin/python` 替换 Windows 的解释器路径。

输入：

```text
我使用的是 MySQL 8.0，请先记住这个对话背景。
我刚才说的数据库版本是什么？
/history
/reset
/history
/exit
```

成功时预期第二轮能利用第一轮提供的背景；具体措辞由真实模型生成，不保证逐字相同。每个普通问题会发出真实模型请求；/history、/reset、/exit 都在本地处理，不发模型请求。输出用量来自服务响应，不是本地猜测。

`/reset` 后只剩 system 消息；退出并重启也会清空本课的进程内历史。重置不会删除供应商已经接收的请求，也不等于清除所有平台记录。

## 8. 关键代码逐步解析

- `Conversation` 的实例表示一个本地会话：每个实例有自己的消息列表，类似后端服务中按 session_id 保存的一份状态。
- `messages` 属性返回字典副本：外部查看列表时，意外修改不会破坏会话内部指令。
- `pending` 是本轮候选请求：复制旧状态再追加问题，真实模型调用成功前不改变已提交历史。
- `invoke` 消费显式传入的消息：同一个模型客户端可以被复用，但会话属于 Conversation，不属于 HTTP 连接池。
- 正文校验后再保存两条消息：防止错误、空正文或被截断输出污染后续上下文。
- 末尾切片只保留完整轮次：system 仍在第一条。当前输入总会被发送；不因裁剪旧轮次而删掉当前问题。
- `reply.usage_metadata` 记录本次服务报告的用量：输入统计包括当次发送的历史，不只是当前 user 这一句；输出统计在推理模型中可能包含不可见的生成用量。

## 9. 项目实践与适用边界

Database Agent 新增的是多轮需求澄清能力，例如先告知数据库类型，再追问只读账号设置。它仍没有数据库工具，不能读取真实 Schema 或执行 SQL。

当前实例只适合单个命令行进程内的纯文本练习，没有持久化、并发锁和用户认证。未来 Web 化时，React 的聊天展示、后端数据库中的聊天归档、某次调用实际发送的上下文应分开设计。保存了完整聊天记录不等于每次都发送全部记录；从工作上下文裁掉旧轮次也不等于必须删除归档。

若重要信息必须长期保留，例如允许访问哪些数据库，应放在经过授权的任务配置或结构化状态中，不能只寄希望于早期聊天不被裁掉。Memory、Checkpoint 与 RAG 在后续课程再分别实现。

## 10. 测试、边界条件与故障排查

测试沿用真实 ChatOpenAI / SDK，只在 HTTP 边界返回固定响应。新增检查：

- 第二次请求确实带上第一次的 user 与真实返回的 assistant。
- 只保留最近 N 个完整轮次，system 与当前问题不丢失。
- 401、超时、空正文和截断时，不改变之前的成功历史。
- 两个会话实例不串历史；reset 保留 system；空输入不请求模型。
- 外部修改 messages 的副本不会改变内部状态。
- 非法轮数在本地拒绝。

这些验证不能证明真实模型一定正确回忆上下文。语义联调还要用自己的模型完成版本问答、引用前一次回答、重置和裁剪实验。

| 现象 | 首先排查 |
|---|---|
| 第二轮不知道第一轮内容 | 检查 /history，是否重启了进程，是否被轮次窗口裁掉 |
| 用量持续增长 | 观察是否在每轮重新发送保留的历史；这是预期机制 |
| 上下文超限 | 单条输入是否很长；keep-turns 只限制轮数，不保证 Token 大小 |
| 没有 Token 用量 | 供应商是否返回 usage；缺失不等于免费或 0 Token |
| 失败后重问重复 | 先区分本地历史是否提交、供应商是否已处理；没有幂等保证时不能假定无重复费用 |
| 找不到 app.chat_cli | 确认使用本课文件包，并在 projects/database-agent 下执行 |

## 11. Summary（本节总结）

- Message 是带角色的消息；Prompt 组织任务；Context 是本次实际提供的信息。
- 本课的多轮连续性来自应用显式传入历史，不来自同一个 API Key 或同一条网络连接。
- Token 不是字数，上下文容量与最大输出是两个相关但不同的约束。
- 本地按完整轮次管理历史，成功后一起提交 user + assistant，失败时不追加半轮。
- 最近 N 轮是一种会丢信息的工作上下文策略，不等于长期记忆或严格 Token 预算。
- 本节成果：真实模型多轮 CLI、历史查看/重置、实际用量显示和异常测试。待完成：你的真实模型联调与理解验收。下一节：Streaming 与 Structured Output。

## 12. 面试题与参考答案

### Q1：同一个 API Key 和同一个 ChatOpenAI 实例，会自动记住之前的聊天吗？

不能据此认为会记住。本课使用的手动 Chat Completions 需要显式提供上下文；Key 用于认证，客户端用于组织请求和连接复用。某些 API 提供服务端会话功能，需要显式按该接口集成，不能与普通模型对象混为一谈。

### Q2：Prompt、上下文窗口和 max_completion_tokens 有什么区别？

Prompt 是给模型的任务输入组织；上下文窗口约束一次调用可处理的总容量；max_completion_tokens 限制生成预算，推理模型还需按规则考虑推理用量。输入历史过大时，不能只调输出参数就认为完成了历史裁剪。

### Q3：为什么不只保存 user 消息？

后续问题可能引用先前 assistant 的方案、编号或解释。缺少实际回答就缺少被引用的内容。纯文本场景应保留完整轮次；有工具调用后，还要保留合法的工具调用和结果关联，不能机械按两条划一轮。

### Q4：如何处理多轮调用失败？

先准备候选消息，等调用和校验成功后再提交状态。失败时保留原历史，并向用户展示错误。网络超时不能证明服务端没执行，重试可能重复费用；工具有副作用时还需要独立的幂等设计。

### Q5：数据库中保存了全部聊天记录，为何模型仍不知道早期内容？

保存归档与构造模型请求是不同职责。只有被装入本次上下文或经服务端会话机制提供的信息，才可能影响本次生成；工作窗口可能裁掉旧内容。对重要约束，应使用结构化状态、受控指令或按需检索，而非依赖无限重发聊天。

## 13. 动手练习与验收标准

1. 使用默认 keep-turns=3 完成“版本背景 → 版本追问”，再 /history，指出 system、user、assistant 各是什么。
2. 将 keep-turns 改为 1，连续完成至少三轮；观察最早背景从本地工作上下文消失。不要把模型猜对数据库版本当成它仍看到旧消息的证据，以实际请求/历史为准。
3. 用 /reset 清空，再检查历史。解释为什么这不等于删除供应商侧记录。
4. 比较第一轮和第二轮服务报告的 input_tokens；不要用 len(question) 解释整个输入用量。
5. 回答预算题：教学假设窗口 8192，预留生成 1000、余量 512，计划输入上限是多少？为什么只限制三轮仍可能超限？

验收：自动测试通过；完成真实服务两轮联调或明确记录阻塞；能画出一次请求的消息顺序；能解释失败不提交与上下文裁剪的取舍。记录到 docs/learning-progress.md，不自动标记学习者已掌握。
